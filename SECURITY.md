# Security Policy

## Supported Versions

| Version | Support Status |
|---|---|
| 0.x (staging) | Active development — security fixes applied on discovery |
| main | Pre-release — security fixes applied within 7 days |

## Reporting a Vulnerability

Report security vulnerabilities to **security@magenta.local** (not the public issue tracker).

**Do not** open a public GitHub issue for security vulnerabilities.

### What to include:
- Description of the vulnerability and impact.
- Steps to reproduce (PoC preferred).
- Affected components (e.g., agent-ops, mcp-bridge, terraform module).
- Suggested fix or mitigation (optional).

### Response timeline:
- **48 hours**: Acknowledgment of receipt.
- **7 days**: Initial assessment and severity classification.
- **30 days**: Fix deployed to staging (critical/high severity).

## Security Architecture

### Authentication
- **Service-to-service**: mTLS for gRPC services, JWT for HTTP services.
- **Cloud authentication**: Azure Workload Identity (OIDC) — no static credentials in code.
- **Agent authentication**: Handled by the MCP Bridge — agents present a JWT issued by the orchestrator.

### Secrets Management
- **Never commit secrets** to the repository. The `config_analyze` tool scans for 5 secret patterns on every PR.
- **Azure Key Vault** stores production secrets (Terraform state keys, vSphere credentials, API keys).
- **K8s Secrets** are generated by `kustomize secretGenerator` from environment files (`.env` files are `.gitignore`d).

### Supply Chain
- **Python dependencies**: Pinned in `uv.lock` (hashed). CI runs `uv sync --frozen` to verify integrity.
- **Docker base images**: Pinned by digest (`python:3.12-slim@sha256:...`).
- **Terraform providers**: Pinned by version (`~> 4.0`, `~> 5.60`). Downloaded from official registries only.

### Network Security
- **Hub-and-spoke**: All cross-cloud traffic flows through Azure hub with NSG/ASG filtering.
- **K8s network policies**: Services within a namespace communicate freely; cross-namespace traffic uses DNS-based policies (future: Istio mTLS).
- **vSphere IL5**: Network-isolated from public cloud, accessible only through site-to-site VPN with IKEv2.

## Container Security

- **Multi-stage builds**: Final images are minimal (`python:3.12-slim`) — no build tools or compilers.
- **Non-root user**: Containers run as `appuser` (UID 1000), not root.
- **Read-only root filesystem**: Config and data volumes are mounted read-only where possible.
- **Health checks**: All services have `HEALTHCHECK` instructions in their Dockerfiles.

## CI/CD Security

- **Terraform state**: Stored in Azure Storage with OIDC auth — no static SAS tokens.
- **Infracost**: Runs on every PR — cost changes are visible but not blocks (information only).
- **Tag compliance**: Fails the PR if >5 resources are missing required tags.
- **Dependabot**: Weekly dependency scans for pip, docker, and GitHub Actions ecosystems.

## Incident Response

1. **Detection**: CI gate failure, budget alert, or manual report.
2. **Triage**: Determine severity (critical/high/medium/low).
3. **Containment**: For critical vulnerabilities, PR a fix to staging, then fast-track to main.
4. **Remediation**: Deploy fix, verify via CI, update CHANGELOG.
5. **Post-mortem**: Document root cause, add ADR if architectural change is needed, update tests.

## Compliance

- **IL5 workloads**: Deployed exclusively to vSphere, tagged with `data-classification: il5`.
- **Data residency**: US commercial data stays in US regions (eastus2, westus2, us-east-1). IL5 data stays in US Gov regions.
- **Audit logging**: All MCP tool invocations are logged via the MCP Bridge with agent ID, tool name, and timestamp.
